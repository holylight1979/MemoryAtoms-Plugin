[Guardian:CoreRules] How to write memory cards
- When the user asks to initialize project memory, or `[Guardian:ProjectMemory]` appears at session start → run `python {code_root}/tools/init-project-memory.py --cwd <project root>`; do not create the folders by hand.
- Always write through the atom_write MCP tool (it validates, dedupes and indexes); never edit a card's .md directly. Cite facts already recorded instead of restating them; do not record temporary attempts or unconfirmed guesses. Every new card starts at [臨] (new [固] / [觀] cards are refused); promotion comes from use or from append. When an injected card clearly saved you or misled you → vote with `atom_feedback(atom_name, verdict=helpful|misleading)` (no vote for cards you did not actually use).
- Realm: useful across projects → `memory/<category>/` (failure family: `memory/Failures/<topic>/`); useful only inside the memory system's own folder → `realm=local`.
- Scope (ask "does this follow the project or the person?"): project rules and decisions → `shared`; only about this person → `personal`; this person's cross-project preferences → `personal, cross_project=true`; every project in the organization should know → `org`.
- Private or sensitive information goes in secret (passwords, tokens, private keys, credentials, personal data, internal addresses, anything you would not publish): call `atom_write` with `secret=true`; it lands in `memory/personal/<user>/secret/` — not version controlled, not sent to the vector service, visible only to its owner, triggers still inject it. Other personal cards (work preferences) stay version controlled as usual. Never write the value itself into a card, only where it is kept. When the write gate flags such wording, decide: plain technical knowledge → pass `not_sensitive=<reason>`; if unsure, treat it as sensitive (moving out of secret is easy, publishing cannot be undone). A card that is partly private → split it in two and put only the private half in secret; the gate refuses secret cards with no private wording or with only some lines matching, so pass `secret_reason=<reason>` only when the whole card really must stay hidden. A card already in the wrong place → move it with `atom_move`.
- create requires `domain` (closed Lv1 list in `memory/_meta/taxonomy.json`); if unsure where it lands, use `dry_run` first; knowledge that fits no category is not written.
- Lists do not go in cards: todos, backlogs, audit results, lookup tables and anything else that keeps growing live in `memory/_staging/<topic>.md`; the card holds only a pointer (where the original is, how to change it, what does not belong here). A card is injected whole on trigger and its knowledge section caps at about 200 tokens, so a long list gets truncated — recorded but never delivered. The write gate refuses cards by todo-marker count (`- [ ]` / `- [x]` ≥ 3).
- When a card hits the budget, first tell whether it is a conclusion or a list: conclusion → compress it (move case narrative to a document); list → change its shape. Do not delete existing content to make room. Raising the write budget does not help; the injection side truncates first.
