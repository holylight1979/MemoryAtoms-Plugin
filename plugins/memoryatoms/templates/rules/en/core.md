# Core rules

> Things already enforced in code by hooks／MCP (Sync reminders, parallel-agent suggestions, research fan-out, domain write refusal, version-context warnings, _INDEX hints) are not repeated here; this file only keeps rules you must know beforehand and rules that have no code gate.

## What this system is
- **Core goal**: accumulate every piece of knowledge and experience, file it by category, and deliver it precisely at the moment it is needed — what should be recalled arrives complete, and nothing irrelevant takes a single line of tokens. Every memory-system trade-off must pass both halves.
- **Three memory layers** (the scope you pick when writing):
  - Root layer `~/.claude/memory/`: knowledge that applies across projects, synced with this system's repo → `global`
  - Organization layer (the organization memory repo connected with `/memoryatoms:org`): organization knowledge and tool cards shared by all projects → `org`
  - Project layer `{project}/.claude/memory/`: that project's decisions and pitfalls, versioned with the project → `shared`／`personal`
- Which layers are connected, and whether the install is complete → the memory system's `tools/install.py --verify` (git install only).

## Governance principles
- **Native-first**: native mechanisms (CLAUDE.md / skills / memory / resume) come first; build your own only for what native cannot do and that is structured · auditable · high-value across sessions. The cure for over-engineering is honesty plus pruning, not a rewrite.
- **Change the root layer only from the root layer**: the `~/.claude` core (hooks/lib/tools/skills/rules, root-layer settings and docs, root-layer repo version control) is changed only in a `~/.claude` session; when a project session runs into it → do not touch it, write the request as a paste-ready prompt for the user (the gate blocks it, and the block message gives the alternative). Running a root-layer tool is not a change: run it by its absolute path (`python "<memory-system folder>/tools/<tool>.py" …`; the hint lines the hooks print give the exact command), without `cd` into it.
- **Observability rule**: every fail-open is "don't block, but tell" — a degradation／silent failure must surface a signal (warning / stderr / closing report); never swallow it.
- **Judgment goes to the LLM, procedure goes to code**: a fixed rule is the product of a judgment already made; anything that still needs judgment (what to test, who is affected, whether it is a false positive) is not hard-coded — leave an entry point where the LLM declares its judgment, gives a reason, and is reconciled later.

## Knowledge base
- Never change code from memory; before asserting severity/blocker/"will definitely break", prove it first (run it / look it up / trace to the root cause). Details [[feedback-未實證先別斷言-從根源驗證-先證再修-反退避反冗長]]
- Changed core structure / new understanding / a pitfall → update _AIDocs + _CHANGELOG.md (sync _INDEX.md when adding); _AIDocs holds only long-term reference; plans/TODOs/work in progress → memory/_staging/.
- Live files (code/config/test) and atoms describe only the current state; do not bury version context in them (version/phase markers, date stamps, change narratives); history goes to `_AIDocs/DevHistory/` and `_CHANGELOG.md`.
- When writing rule files and decision cards: write the current practice as "currently uses X", not "always"; for a rollback or rejection, say whether the direction was wrong or the timing／resources were not there — write only the conclusion, because the next AI will read it as a prohibition.

## Memory
- When the user says "初始化原子記憶庫" (initialize the atom memory) or `[Guardian:ProjectMemory]` appears at session start → run the memory system's `tools/init-project-memory.py --cwd <project root>` (the `[Guardian:ProjectMemory]` hint prints the exact command); do not create the folders by hand.
- Writes currently go through the atom_write MCP (automatic validation, dedup, indexing); never Edit an atom .md directly; cite facts already recorded; do not write temporary attempts/unconfirmed guesses. **New atoms currently start at [臨]** (the system rejects new [固]/[觀]); promotion comes from use or append. When an injected card clearly saved you or led you astray → cast one vote with `atom_feedback(atom_name, verdict=helpful|misleading)` (do not vote on cards you did not actually use).
- **Realm**: applies across projects → `memory/<domain>/` (failure family `memory/Failures/<topic>/`); useful only inside ~/.claude → `realm=local` (`memory/_local/`). Three questions: ① reusable in ≥2 projects? ② a system rule, or the domain of a specific app／tool／environment? ③ valid for months or for weeks? Leaning to the first answer → core, to the second → local; when unsure, go core ([[realm判core還是local-問換一個不用記憶系統的專案還用不用得上-例子取自記憶系統不算local-拿不準回core]]).
- **Scope** (ask "does it follow the project or the person?"): the project's rules／decisions → `shared`; only about this person → `personal`; this person's cross-project preferences → `personal, cross_project=true`; every project in the organization should know it → `org`.
- **Personal sensitive information goes in secret** (passwords, tokens, private keys, credentials, personal data, internal network addresses, any verification or private content you do not want public): call `atom_write` with `secret=true`; it lands in `memory/personal/<user>/secret/` — not version-controlled, not sent to vectors, only for this person, triggers still inject it. Other personal cards (work preferences) are version-controlled as usual; no need to hide them. Do not write the value itself into the card; write only where it is kept. When the write gate hits related words it asks you to judge: if it is only general technical knowledge, pass `not_sensitive=<reason>`; when unsure, treat it as sensitive (moving out of secret later is easy; once public it cannot be taken back). **A card that is partly private and partly not → split it into two**, and only the private half goes into secret; the write gate blocks secret cards with no private words at all, or where only some lines match; pass `secret_reason=<reason>` only when the whole card truly must be hidden. Move a card written to the wrong place with `atom_move` (in or out).
- create must pass `domain` (the closed Lv1 list in `memory/_meta/taxonomy.json`); if unsure where it lands, `dry_run` first; knowledge whose domain you cannot tell is not written.
- **Lists do not go into atoms**: things that keep growing — todos／backlog／audit results／lookup tables — have their master copy in `memory/_staging/<topic>.md`; the atom keeps only a pointer (where the master is／how to change it／what does not go here). An atom is injected whole with its trigger, and the knowledge section is capped at about 200 tok by default (up to 400 when the budget allows), so long lists still get truncated — putting them in means recorded but never delivered. The write gate hard-rejects by checkbox count (`- [ ]`／`- [x]` ≥3).
- **Prohibitions in Failures cards carry a context**: when a new `[臨]` line in the Failures domain contains 「一律／不准／禁止／必須／嚴禁／不得」 (always／not allowed／forbidden／must／strictly forbidden／must not), that line or the next needs a context marker — 「情境：」 (context), 「何時：」 (when) or 「適用：」 (applies to) — saying when it applies and when it does not; without one the write gate rejects it. A prohibition written in the moment of a failure without a context gets used to overrule the user's new goals and collides with other cards. Only new cards and newly appended lines are checked.
- When an atom is blocked by the budget, first tell **whether it is a conclusion or a list**: conclusion → compress it (move case narratives to docs); list → change its shape. Do not delete existing content to make room. Raising the write budget does not help; the injection side truncates first.

## Version control
- **Memory cards and indexes are synced by the system** (if you turned sync on): cards and indexes of all three layers are uploaded by the background sync — the AI neither touches nor asks; do not run the full suite just to commit.
- **Code and doc changes wait for the user's command word** (including the atom memory system's own code and docs) (team property; uploading is deciding for others): after changing, only report what changed and what was verified; wait for the user to read the diff and give the version-control command word (by default e.g. "push to git"; the list is `commit_order.keywords` in `workflow/config.json`), then commit → push in one go.

## Conversation
- "用識流…" (use the consciousness stream) → /memoryatoms:consciousness-stream; /resume → /memoryatoms:continue.
- An independent subtask may move to a new conversation; make sure the knowledge is saved before splitting; context compaction about to happen → remind the user to open a new session.
- **Reading in Plan Mode** currently uses the Read / Grep / Glob tools, not Bash cat/grep/sed instead (Plan Mode suspends bypass, and Bash must pass a read-only check that pops a prompt); Bash commands get no `cd <folder>` prefix — write absolute paths directly.
- Parallel sub-agents／knowledge-retrieval fan-out: with the workflow-nudge extension installed, the hook hints when it matches; **when it does not match (or is not installed) but would clearly benefit** (several non-conflicting facets／"look this up for me"・"research this" requests), still evaluate it yourself; criteria [[workflow-parallel-agents]], [[workflow-research-fanout]].
